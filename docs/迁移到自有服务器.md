# 从 Supabase 迁移到自有服务器 — 评估与方案

> 结论先行：**本项目的后端不是"一个数据库"，而是一整套 Supabase 服务栈**。迁移 ≠ 换连接字符串，而是按「你想甩掉 Supabase 的哪一层」来选择路线。

---

## 1. 现状：到底依赖了 Supabase 的哪些能力

| 能力 | 是否使用 | 规模 |
|---|---|---|
| PostgreSQL 数据库 | ✅ | 25 张业务表 |
| 存储过程 / 触发器函数 | ✅ 重度 | **30 个** plpgsql 函数 + 8 个触发器（`security definer`） |
| RLS 行级安全 | ✅ 重度 | 整个权限模型建立在 RLS 之上 |
| Auth（邮箱注册/登录/JWT/重置密码） | ✅ | `src/api/auth.ts` + `stores/auth.ts` |
| Storage（选手截图上传） | ✅ | `player-screenshots` bucket |
| Realtime（`postgres_changes` 订阅） | ✅ | `src/api/match.ts` 积分榜/赛程实时刷新 |
| Edge Function（Deno 运行时） | ✅ | 1 个：`pwa-proxy`（完美平台 CORS 代理） |

**前端耦合度**：21 个文件、约 74 处 `supabase.*` 调用，全部通过 `@supabase/supabase-js` 和 `src/lib/supabase.ts` 这一层。API 层（`src/api/*.ts`）已经做了隔离，这是好事——**迁移不需要改视图层**，只需动 `api/` + `lib/` + `stores/`。

---

## 2. 三条迁移路线

### 路线 A：自托管 Supabase（推荐，成本最低、改动最少）

用 [supabase/supabase](https://github.com/supabase/supabase) 官方 Docker 编排，在自己服务器上跑一套完整 Supabase。

- **改动**：仅改两个环境变量 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` 指向自托管实例。代码零改动。
- **保留**：Auth、RLS、Storage、Realtime、30 个函数、Edge Function 全部原样可用。
- **代价**：Supabase 官方栈较重（Postgres + GoTrue + Realtime + Storage + PostgREST + Kong + Edge Runtime，约 10 个容器，建议 ≥4G 内存）。
- **Edge Function 处理**：自托管 Supabase 支持本地 `functions serve`；`pwa-proxy` 逻辑简单，也可直接改成用 Cloudflare Worker 或 nginx 反代，摆脱 Deno 运行时。

> 你的服务器（140.143.184.247）跑过 TS3、SFTP、CS2 战术板等多个服务，属于熟手环境，这条路线对你成本最低。

### 路线 B：换成 PostgREST + 自建鉴权（去 Supabase，只留 Postgres）

把 Supabase 拆掉，保留 Postgres，用 [PostgREST](https://postgrest.org) 提供 REST API，自建 Auth（如 [GoTrue](https://github.com/supabase/gotrue) 单跑、或 Keycloak、或极简 JWT 签发服务）。

- **改动**：`src/lib/supabase.ts` 换成 PostgREST 客户端；`api/` 层改动小（PostgREST 语法与 supabase-js 高度同源，因为 supabase-js 底层就是 PostgREST）；Auth 调用需重写。
- **代价**：
  - **RLS 可直接沿用**（PostgREST 原生支持，JWT 里的 `sub`/`role` 就是 Supabase 同款 claim）。
  - **30 个函数 + 8 个触发器原样保留**（纯 Postgres，与 Supabase 无关）。
  - **Realtime 要自己补**：换 [supabase/realtime](https://github.com/supabase/realtime) 单跑，或退化为轮询。
  - **Storage 自己补**：自建 S3（MinIO）或本地文件服务。
  - **Edge Function 自己补**：`pwa-proxy` 改 nginx 反代。
- **适合**：想彻底摆脱 Supabase 品牌/账单，但接受自建 Auth + Realtime + Storage 的运维量。

### 路线 C：改造成自建 REST 后端（最彻底，但最贵）

用 Node/Python 自写后端，逐表暴露接口，前端 `api/` 层全部重写。

- **代价最大**：30 个 plpgsql 函数（下注结算、论坛点赞计数、淘汰赛自动生成对阵、阶段统计自动刷新等）全部要用业务代码重新实现，其中不少是**触发器级的数据一致性逻辑**，重写极易出 bug。
- **不建议**：除非你有明确理由（团队不想维护 SQL、要引入自己的中间件生态），否则纯属把已经跑通的东西重造一遍。

## 3. 建议

| 诉求 | 选哪条 |
|---|---|
| 只是想把数据攥在自己手里 / 摆脱 Supabase 云账单 | **路线 A**（自托管 Supabase） |
| 想要"自己的数据库 + 自己的域名 API"，不介意多写点运维 | **路线 B**（PostgREST + 自建鉴权） |
| 团队要全面转向自研后端 | 路线 C（慎重，性价比低） |

**通用建议**：无论哪条，先做一次 **schema.sql 在裸 Postgres 上的可迁移性检查**——当前 schema 里有几处 Supabase 特有依赖需要先确认：

1. `storage.buckets` / `storage.objects`（第 97–113 行）——这是 Supabase Storage 的内建 schema，裸 Postgres 上没有，路线 B/C 需剔除或替换。
2. `auth.users` 引用（`handle_new_user` 触发器）——依赖 Supabase Auth 的内建表，路线 B/C 需换成自建用户表。
3. `realtime` 发布/订阅——schema 里未见显式 `alter publication`，说明 Realtime 是控制台默认开启的，迁移后需重新配置。
4. Edge Function `pwa-proxy` 是 Deno 运行时，自托管 Supabase 之外的环境需重写成别的形式。

---

## 4. 迁移检查清单（路线 A 落地版）

1. 服务器装 Docker（你已有）+ 拉 `supabase/supabase` 编排。
2. 在自托管实例 SQL 编辑器执行 `supabase/schema.sql`（含全部 migration，注意顺序）。
3. 部署 `pwa-proxy` Edge Function（或改 nginx 反代）。
4. 前端 `.env.local` 的 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` 指向自托管实例。
5. 配置 Auth 邮箱 SMTP（重置密码邮件）、Storage 上传域名白名单、Realtime 表订阅。
6. 数据迁移：Supabase 云 → 自托管，用 `supabase db dump` + `supabase db restore` 或 `pg_dump`。
7. 重跑端到端验证：注册 → 报名 → 审核 → 录入比分 → 积分榜实时刷新 → PWA 导入。
